# SQL grammar conflict diagnosis (2026-11-15)

This document records the original `MsSqlDialectFeatures.All` conflict inventory, the first two targeted grammar corrections, and the stage-3 procedure-body boundary investigation. The reproducible reports are generated by `MsSqlGrammarConflictDiagnosticsTests` and uploaded as `sql-grammar-conflicts.md` in the **Build and Test** workflow artifacts. No parser conflict-resolution algorithm was changed.

## Concrete ambiguity examples

1. **Identifier versus expression (baseline state 396, now fixed):**
   `PrimaryExpression → SqlcmdVariable` competed with
   `StrictIdentifierTerm → SqlcmdVariable` across 132 distinct lookaheads.
   Removing the direct `PrimaryExpression` production eliminated all 133 occurrences.

2. **Column DEFAULT expression (baseline states 3764 and 3453, now fixed):**
   `CreateTableColumnConstraintBody → DEFAULT ( Expression )` and
   `CreateTableColumnOption → DEFAULT ( Expression )` overlapped with
   `PrimaryExpression → ( Expression )`. Removing the two redundant parenthesized DEFAULT alternatives eliminated all 134 occurrences (67 in each group). The equivalent `DEFAULT Expression` alternatives remain.

3. **Procedure body boundaries (four states):**
   Four productions of `CreateProcBodyBlock` compete with shifts for many
   possible subsequent statement-leading tokens. This suggests a boundary/optional-separator issue requiring focused examples.

4. **IF/ELSE (state 1551):**
   `IfStatement` versus `StatementNoLeadingWith` produces 46 R/R occurrences.
   This is separate from the explicitly resolved dangling-`ELSE` S/R conflict and needs targeted nested-IF tests.

Remaining unresolved examples are hypotheses based on the table diagnostics; they do not yet establish which production should win or whether LALR state merging contributes.

## Proposed fix sequence

1. **Completed:** remove the redundant SQLCMD primary-expression reduction; confirm positive/negative parsing, parse-tree shape, and formatter round trips.
2. **Completed:** remove the two redundant column-level `DEFAULT ( Expression )` alternatives and verify their replacement via `DEFAULT Expression`.
3. **Investigated (stage 3):** the 172 `CreateProcBodyBlock` shift/reduce occurrences arise from an unresolved choice between completing an unwrapped procedure/trigger body and continuing its statement sequence. Local alternatives were tested but not merged because they violate compatibility or introduce new unresolved conflicts (details below).
4. Investigate `IF/ELSE` and keyword-sensitive name/option contexts.
5. Only after reviewing conflicts, introduce an **opt-in strict grammar build** that rejects unresolved entries. Do not change the default behavior of unrelated grammars without a compatibility plan.

Avoid suppressing conflicts with blanket `OnShiftReduce` rules: R/R conflicts and grammar ambiguities require evidence-driven grammar changes.

## First targeted fix: SQLCMD expression versus identifier (2026-11-15)

**Cause.** `MsSqlExpressionGrammar.Build` accepted `SqlcmdVariable` both directly via
`PrimaryExpression → SqlcmdVariable` and indirectly via
`PrimaryExpression → QualifiedName → ContextualIdentifierTerm → StrictIdentifierTerm → SqlcmdVariable`.
The two reductions overlapped in one LR state, and reduce/reduce resolution
depended on production registration order.

**Change.** Remove only `gb.Prod(primaryExpression).Is(sqlcmdVariable);`.
Keep `StrictIdentifierTerm → SqlcmdVariable` unchanged. A SQLCMD placeholder in an
expression now follows the existing `QualifiedName` path; a placeholder in a
database/table/schema name continues through its identifier context. The
`SqlcmdVariable` terminal is unchanged, including its name, regular expression,
and original source text. The SQL formatter sees the same significant tokens;
the intermediate `QualifiedName`, `ContextualIdentifierTerm`, and
`StrictIdentifierTerm` nodes replace the former direct expression reduction
where that path was previously chosen.

**Before/after diagnostics** (full reports generated by the same `All`-dialect test):

| Metric | Before | After | Delta |
| --- | ---: | ---: | ---: |
| Productions | 2,196 | 2,195 | -1 |
| LR states | 3,954 | 3,953 | -1 |
| Registered conflicts | 1,206 | 1,073 | -133 |
| Unresolved shift/reduce | 382 | 382 | 0 |
| Unresolved reduce/reduce | 823 | 690 | -133 |
| Explicitly resolved shift/reduce (`ELSE`) | 1 | 1 | 0 |
| LR states containing conflicts | 81 | 80 | -1 |
| Target `PrimaryExpression` / `StrictIdentifierTerm` reductions | 133 | 0 | -133 |

The full reports were compared by conflict kind, lookahead, resolution,
and both production texts, rather than by unstable LR state numbers. Exactly
133 occurrences disappeared (132 distinct lookaheads, including two on
`WITH`); **no new conflict families or occurrences appeared**. All other
conflict groups remained identical.

**Regression results.** GitHub Actions passed the full solution restore/build
(including the WebAssembly project) and **578/578 tests**, up from 552 baseline
tests. Coverage collection and the conflict-report artifact also succeeded.
New tests cover SQLCMD identifiers, arithmetic/CASE/INSERT expressions,
qualified table names, malformed substitutions, terminal text and tree paths,
and `Parse → Format → Parse → Format` idempotence, including `GO` and `:setvar`.
The existing `ParseScript_ShouldParseSqlcmdVariables_AsIdentifiersAndExpressions`
test passed. The explicitly resolved `ELSE` behavior remained intact.

One example needed adjustment without changing grammar rules: the unquoted
alias `AS Result` was rejected as a keyword where the current grammar expects
an identifier. The tests use `AS [Result]` instead. This is a separate alias
restriction, not a SQLCMD-expression failure; the grammar was not broadened
for this conflict-fix stage.

Evidence: baseline [Build and Test run](https://github.com/DimonSmart/dslkit/actions/runs/43693445918)
and changed [Build and Test run](https://github.com/DimonSmart/dslkit/actions/runs/43698812473),
each with a full `sql-grammar-conflicts.md` artifact.

## Second targeted fix: column DEFAULT parentheses (2026-11-15)

**Cause.** Two column-level alternatives explicitly accepted parentheses around a DEFAULT value:

```csharp
gb.Prod(createTableColumnOption).Is("DEFAULT", "(", expression, ")");
gb.Prod(createTableColumnConstraintBody).Is("DEFAULT", "(", expression, ")");
```

Both competed with the existing `DEFAULT Expression` path, because
`MsSqlExpressionGrammar` already defines `PrimaryExpression → ( Expression )`.
The original full report identified **67 reduce/reduce occurrences** for
`CreateTableColumnOption` versus `PrimaryExpression`, and **67** for
`CreateTableColumnConstraintBody` versus `PrimaryExpression`, across their
lookaheads. The conflict was an actual duplicate derivation, not merely a
guess based on common parentheses syntax.

**Change.** Remove exactly the two productions above. Keep both
`DEFAULT Expression` productions, `PrimaryExpression → ( Expression )`,
and all `CreateTableTableConstraintBody` productions unchanged.
Nested `DEFAULT ((0))` and function/arithmetic expressions remain supported
through recursive expression parsing. No lexer, LR parser, formatter, or
conflict-priority changes were required.

**Before/after diagnostics** (same `MsSqlDialectFeatures.All` diagnostic test,
comparing the full CI artifacts, before on `master`, after on the PR):

| Metric | Before | After | Delta |
| --- | ---: | ---: | ---: |
| Productions | 2,195 | 2,193 | -2 |
| LR states | 3,953 | 3,947 | -6 |
| Registered conflicts | 1,073 | 939 | -134 |
| Unresolved reduce/reduce | 690 | 556 | -134 |
| Unresolved shift/reduce | 382 | 382 | 0 |
| Explicitly resolved shift/reduce (`ELSE`) | 1 | 1 | 0 |
| LR states containing conflicts | 80 | 78 | -2 |
| Target column-constraint DEFAULT / primary-expression collisions | 67 | 0 | -67 |
| Target column-option DEFAULT / primary-expression collisions | 67 | 0 | -67 |

The **full conflict-family multiset** was compared using the conflict kind,
lookahead terminal, exact existing and incoming production text, resolution
status, and occurrence multiplicity. LR state numbers were deliberately
excluded from the keys. Exactly 134 occurrences and 134 distinct families
disappeared; **zero new occurrences/families** were introduced, and
**all 939 remaining occurrences** retained the same keys and multiplicities.
The unchanged `CreateTableTableConstraintBody` parenthesized alternative
was inspected but not altered in this stage.

**Regression results.** The new tests first passed unmodified grammar in
[the pre-change Actions run](https://github.com/DimonSmart/dslkit/actions/runs/43701100089)
(**603/603 tests**), establishing that positive examples were already supported.
With the two productions removed and a focused conflict-absence assertion
added, [the changed Actions run](https://github.com/DimonSmart/dslkit/actions/runs/43701289131)
passed the full solution Build and Test (**604/604 tests**, no failures).
Coverage and report generation completed successfully.

Regression cases exercise unparenthesized, single- and double-parenthesized
DEFAULT; named column constraints; `GETDATE()` and arithmetic values;
`NULL` and `NOT NULL` alongside DEFAULT; CREATE TABLE without DEFAULT;
ALTER TABLE ADD via shared column-definition productions; malformed empty,
unclosed, and missing DEFAULT values; token text and parse-tree context for
named and unnamed defaults; and `Parse → Format → Parse → Format` idempotence
with significant-token preservation. No unsupported SQL variants were added
as part of this grammar correction.

**Next priority:** investigate procedure body boundaries
(`CreateProcBodyBlock`: 172 unresolved shift/reduce occurrences over four
LR states), using concrete multi-statement procedure regression cases before
changing grammar.

## Stage 3: unwrapped procedure and trigger body boundaries (2026-11-15)

**Status: confirmed blocker; no production grammar change merged.** The explicit
`ELSE` resolution remains untouched. The original eight `CreateProcBodyBlock`
alternatives are retained because neither of the tested local reductions meets
the stage-3 acceptance criteria.

### Conflict analysis

The [full baseline report](https://github.com/DimonSmart/dslkit/actions/runs/43701758266)
from `8c0d3bc2be05` contains 172 unresolved shift/reduce occurrences:
exactly 43 lookaheads for each of these four reductions:

| Reducing production | Occurrences |
| --- | ---: |
| `CreateProcBodyBlock → StatementList` | 43 |
| `CreateProcBodyBlock → StatementList StatementSeparatorList` | 43 |
| `CreateProcBodyBlock → StatementSeparatorList StatementList` | 43 |
| `CreateProcBodyBlock → StatementSeparatorList StatementList StatementSeparatorList` | 43 |

The 43 lookaheads are `;` plus 42 statement-leading terminal kinds:
`ALTER`, `BEGIN`, `BREAK`, `BULK`, `BracketIdentifier`,
`CHECKPOINT`, `CLOSE`, `COMMIT`, `CONTINUE`, `CREATE`, `DBCC`,
`DEALLOCATE`, `DECLARE`, `DELETE`, `DROP`, `EXEC`, `EXECUTE`,
`FETCH`, `GOTO`, `GRANT`, `IF`, `INSERT`, `Id`, `MERGE`,
`OPEN`, `PRINT`, `QuotedIdentifier`, `RAISERROR`, `RETURN`,
`REVERT`, `ROLLBACK`, `SAVE`, `SELECT`, `SET`,
`SqlcmdVariable`, `THROW`, `TRUNCATE`, `TempIdentifier`,
`UPDATE`, `USE`, `WAITFOR`, and `WHILE`.

The full report includes the shift-capable LR items for each family.
For `;` the competing item starts `StatementSeparator → ● ;`.
For other lookaheads the shift path begins another statement in the shared
`StatementList`. The reduce path finishes the unwrapped procedure or trigger
body and allows the enclosing `Script` to continue. The same next token can
legally start another statement in either context under the current permissive
grammar. The four affected LR states are *not* used as stable identifiers.

The four productions for explicitly delimited `BEGIN ... END` /
`BEGIN ATOMIC ... END` do **not** generate this 172-case cluster.
`GO` is consumed by `SqlServerScriptPreprocessor` before each batch is
parsed and cannot by itself disambiguate the LR table.

### Experiments and results

Regression tests were committed *before* either grammar experiment.
[Baseline with tests](https://github.com/DimonSmart/dslkit/actions/runs/43703199439):
**627 passed**; all baseline conflicts unchanged.

**Experiment 1 — remove the two trailing-separator alternatives from
unwrapped bodies.** This does not preserve the runtime parser's shift
behavior: a semicolon after the final procedure statement is shifted, but the
body cannot then be completed at EOF. Four new regression cases fail, including
a three-statement body and a document separated by `GO`.
[Failed CI run](https://github.com/DimonSmart/dslkit/actions/runs/43703398131).
The change was rejected.

**Experiment 2 — factor the unwrapped body into optional leading separators,
`StatementList`, and optional trailing separators.** All **627 tests passed**,
but [the full conflict report](https://github.com/DimonSmart/dslkit/actions/runs/43703633757)
contains new unresolved collisions. The complete multiset comparison uses
(kind, lookahead, existing production, incoming production, resolution,
occurrence count), **never LR-state numbers**.

| Diagnostic | Baseline | Factored experiment | Final retained grammar |
| --- | ---: | ---: | ---: |
| Total conflicts | 939 | 860 | 939 |
| Unresolved shift/reduce | 382 | 303 | 382 |
| Unresolved reduce/reduce | 556 | 556 | 556 |
| Explicitly resolved (ELSE) | 1 | 1 | 1 |
| `CreateProcBodyBlock` S/R occurrences | 172 | 0 | 172 |
| LR states | 3,947 | 3,949 | 3,947 |

Relative to the baseline, the factored experiment **removed 174** conflict
occurrences (172 targeted cases and two `StatementListOpt` cases) but
**added 95** new unresolved entries:

- 43 on `CreateProcBodyTrailingSeparatorsOpt → Empty`;
- 43 on `CreateProcBodyTrailingSeparatorsOpt → StatementSeparatorList`;
- 9 on `CreateProcBodyLeadingSeparatorsOpt → Empty` (lookahead `BEGIN`).

The other 765 original conflict occurrences remained unchanged. Thus this
merely relocates the underlying boundary ambiguity and introduces nine
additional collisions: the lower total is **not** a valid fix under the
no-new-conflicts criterion. The experiment was rejected and the grammar
restored byte-for-byte.

### Regression coverage and formatter

`MsSqlCreateProcBodyRegressionTests.cs` adds cases covering `CREATE PROC`,
`CREATE PROCEDURE`, `ALTER PROCEDURE`, `CREATE OR ALTER PROCEDURE`,
one- and multi-statement bodies, unwrapped and `BEGIN/END` bodies,
leading, consecutive and trailing semicolons, `DECLARE` / `SET` / `SELECT`,
`IF/ELSE`, nested blocks, CLR external names, triggers, `GO`, invalid and
unclosed definitions, and three-statement parse-tree containment. Existing
programmable-object and procedural tests additionally exercise `WHILE`,
`RETURN`, native `BEGIN ATOMIC`, `TRY/CATCH`, SQLCMD placeholders, and
SQL Server examples.

The formatter regressions perform
`Parse → Format → Parse → Format` in all three
`SqlStatementTerminationMode` modes and both `SqlCreateProcLayout` modes.
They check repeated-format stability, comment preservation, significant
non-semicolon tokens and that `SELECT` values remain under
`CreateProcBodyBlock`. The formatter implementation was not changed.

**Blocker:** eliminating every remaining boundary collision requires an
unambiguous policy for when an unwrapped procedure or trigger body ends in a
batch. Strict SQL Server batch scoping would be one answer, but applying it
globally would reject formerly accepted scripts with additional statements
or definitions in the same batch. Neither lexer changes nor parser conflict
resolution overrides are justified by the current evidence.

See [the follow-up specification](sql-procedure-body-batch-boundary-followup.md)
for the separate, compatibility-aware design decision. It is **not** part of
stage 3.
